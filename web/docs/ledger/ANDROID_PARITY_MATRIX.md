# Android capability-parity matrix

Generated by hand from source (Phase 1H), **not** by a script. Web `integration/phase0-recovery` @ `0358f14` (audit baseline; updated through Phase 1I); Flutter `integration/phase0-recovery` @ `0ffaf80` (audit baseline) → `2542923` (Slice 1) → `7bc6213` (Slice 2, Phase 1I) → `93c7aa5` (Slice 3, Phase 1J).
The generated route ledger (44 pages, 91 route files / 150 handlers, 33 Android route paths) and static caller scans are only *leads*: a static scan cannot see calls made through helper wrappers (e.g. `_api.post('/uploads/sign')`, `fetchReceiptBytes('/api/rms/…')`) and says nothing about behaviour, so every row below was read in source on both sides.

## How to read it
**Status** (only these five): `MATCHED` — equivalent behaviour implemented *and* verified at the evidence level shown · `PARTIAL` — some of the workflow exists, or it exists but equivalence was not verified · `MISSING` — no functional Android equivalent · `BLOCKED` — needs a live service, owner decision or external configuration · `PLATFORM EXCEPTION` — deliberate exclusion with a documented, approved reason. **No row is currently a PLATFORM EXCEPTION: no exclusion has been approved**; candidates are marked `BLOCKED (owner decision)`.

**Evidence** — `E1` source read on both sides only · `E2` Flutter unit/widget tests of the workflow · `E3` live contract test of the real Flutter client against a disposable backend (fake providers) · `E4` physical Samsung SM-S721B, QA build, local disposable backend (Phase 1D–1F sessions). A row is `MATCHED` only at `E2` or higher *and* only where the Android flow covers the Web flow's meaningful actions and states. Anything verified only by reading (`E1`) is at best `PARTIAL (unverified)`.

**Roles / entitlements.** Employee / Manager / Admin are server roles; every API method re-checks role and organisation. Entitlement is the persisted org record: Public Free `free/none/webEnabled=false/androidEnabled=true`, Public Premium `premium/subscription/webEnabled=false/androidEnabled=true`, Doppelmayr lifetime grant `premium/lifetime_grant/webEnabled=true/androidEnabled=true` (pinned by `tests/entitlement_matrix_mobile_web.test.js`; Android sign-in and `/auth/me` hydration for all three verified at E3/E4). Public organisations are Android-only by design — Web access needs `webEnabled`. No row may rely on an organisation name, slug or id (`tests/web_access_boundary.test.js` D2 enforces this in runtime code). Premium-gated rows are marked `P`; the Android client reads gates from `/auth/me` (`entitlements.features`), never from the plan name.

## Notes on evidence
* **Live suite caveat (resolved in Phase 1I).** At the audit baseline `test/integration/expense_e2e_test.dart` failed with 409. Diagnosis on a fresh disposable database: the test's second `POST /api/rms` (same `clientRequestId`, same receipt URL — a retry/double-tap) returned `409 {"error":"That receipt is already attached to another expense.","code":"attachment_in_use"}`, while the same retry without receipts returned 200 with the original claim. It was a **genuine contract defect**, not a test assumption: the receipt-attachment check ran before the idempotency lookup. Fixed in `app/api/rms/route.ts` (idempotency first) with `tests/expense_idempotency_receipts.test.js`. A second defect was found by the new live test: `PATCH lineItems.99.status` padded a 3-line claim to 100 lines (later writes then failed with 500); fixed with an index bound and `tests/expense_line_review_bounds.test.js`. With both fixes the whole `test/integration` folder passes serially on a fresh database (the earlier CRM/receipt-OCR failures were not reproduced).
* The live suites are not re-runnable on a used database (registration slugs, seat limits, per-account rate limits); every verification here used a fresh disposable database.
* Nothing in this matrix was verified against a production service, real Gemini, real Cloudinary, SMTP, Outlook or Google Play.

## Slice 3 — Leave medical documents (closed, Phase 1J)

Security finding first: the Web leave form uploaded with `kind=document` (publicly deliverable) and `POST /api/lms` accepted arbitrary strings. Fixed on Web (purpose-bound private tickets, server-issued refs only, authenticated per-read retrieval) and consumed by Android. Live contract test (`leave_medical_e2e_test.dart`) ran against a disposable backend with fake storage. Legacy records still need the documented migration. See `docs/LEAVE_MEDICAL_DOCUMENTS.md`.

## Slice 2 — Itemised expense claims (closed, Phase 1I)
Flutter `7bc6213`: typed `ExpenseLineItem` (all server fields, status parsed fail-safe to pending), integer-paise money (`money.dart`), `LineItemsController` + `LineItemsEditor` (add/edit/remove rows, description/amount/category/date/receipt, 50-row cap, live exact total, per-field messages revealed on submit), single/itemised switch in the expense form, revision of returned itemised claims with kept/new line receipts, full breakdown with statuses and rejected-aware total in the detail sheet, role-authorised per-line approve/reject with single-flight guard, server-error mapping to plain sentences. Not tested: physical device, real Cloudinary, TalkBack, stored-PDF preview, print/export (X7).

## Statement
Parity is **not** claimed. Of 70 capability rows: 20 MATCHED (including T4, X2 and L4 — images only — and the Android-only A12), 28 PARTIAL, 15 MISSING, 4 BLOCKED (A4, X7, C12, M10), 0 PLATFORM EXCEPTION, 3 are not Android capabilities. Most PARTIAL rows exist on Android but have never been compared field-by-field with Web or exercised against a live backend; they are not evidence of parity.
